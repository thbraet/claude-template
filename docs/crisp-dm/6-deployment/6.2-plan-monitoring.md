# 6.2 Monitoring and Maintenance Plan

> **Project:** Titanic Survival Prediction
> **Date:** 2026-03-31
> **CRISP-DM Phase:** 6. Deployment
> **Status:** Draft

---

## Applicability Note

**This project is a one-time Kaggle submission, not a production deployment.** There is no ongoing serving, no incoming data stream, and no ground truth feedback loop after submission. Kaggle does not release test-set labels, so post-submission performance monitoring is limited to the single leaderboard score.

This document serves an **educational purpose**: it documents what a monitoring and maintenance plan would look like if this model were deployed in a production setting (e.g., predicting outcomes for an ongoing classification task). This fulfills the CRISP-DM 6.2 requirement and the model governance mandate that "a monitoring plan is required before any model goes to production."

---

## Monitoring Overview

- **Model in Production:** XGBoost (tuned, `n_estimators=100`, `max_depth=6`, `learning_rate=0.05`)
- **Baseline Performance:** Accuracy = 84.73% (OOF on 891 training rows, 2026-03-31)
- **Minimum Acceptable Performance:** Accuracy >= 80% (BSC2)
- **Ground Truth Lag:** Infinite for Kaggle (test labels never released); in a production scenario, this would depend on the business process
- **Monitoring Tool:** MLflow (experiment tracking); manual CSV validation for submission
- **Dashboard Location:** Local MLflow UI (`mlflow ui` → `http://localhost:5000`)

## Data Drift Monitoring

### Applicability

For this Kaggle project, data drift monitoring is **not applicable** — the dataset is static and historical (1912). There are no new data arrivals that could drift from the training distribution.

### Educational: What Would Be Monitored in Production

If this model were deployed on a recurring data stream (e.g., predicting outcomes for new passengers on an ongoing basis), the following features would be monitored for distribution shifts.

#### Feature Drift

| Feature | Type | Test | Reference Window | Warning Threshold | Critical Threshold | Frequency |
|---------|------|------|-----------------|-------------------|-------------------|-----------|
| Sex | Categorical | Chi-squared | Training data (891 rows) | p < 0.05 | p < 0.01 | Per batch |
| Pclass | Categorical | Chi-squared | Training data | p < 0.05 | p < 0.01 | Per batch |
| Age | Continuous | KS test | Training data | KS > 0.10 | KS > 0.20 | Per batch |
| Fare | Continuous | KS test | Training data | KS > 0.10 | KS > 0.20 | Per batch |
| FamilySize | Discrete | Chi-squared | Training data | p < 0.05 | p < 0.01 | Per batch |
| Title | Categorical | Chi-squared | Training data | p < 0.05 | p < 0.01 | Per batch |
| Embarked | Categorical | Chi-squared | Training data | p < 0.05 | p < 0.01 | Per batch |
| HasCabin | Binary | Proportion test | Training data (23% have cabin) | Absolute shift > 5pp | Absolute shift > 10pp | Per batch |

**Rationale for feature selection:** These are the top features by importance (4.4) and the features with known distributional properties (2.3). Raw features like Name, Ticket, and Cabin are excluded — their engineered derivatives (Title, HasCabin) are monitored instead.

**Note on train/test consistency (from 2.4):** KS tests on the Kaggle train/test split showed no significant distributional differences for Pclass (p=0.96), Age (p=0.70), SibSp (p=0.99), Parch (p=1.00), Fare (p=0.75), Sex (p=0.63). Only Embarked showed a significant shift (p<0.05), but it is a weak predictor (Cramer's V=0.172). This confirms the reference distributions are stable between train and test for this dataset.

#### Label Drift

| Target Variable | Test | Warning Threshold | Critical Threshold | Frequency |
|----------------|------|-------------------|-------------------|-----------|
| Survived | Proportion test | Survival rate shifts >5pp from 38.4% training rate | Shift >10pp | Per batch (when actuals available) |

#### Schema Drift

| Check | Description | Frequency |
|-------|-------------|-----------|
| Column presence | All 11 expected input columns exist (PassengerId through Embarked) | Every batch |
| Data types | PassengerId (int), Age (float), Fare (float), Sex/Embarked (string), etc. | Every batch |
| Value ranges | Age 0-100, Fare >= 0, Pclass in {1,2,3}, Sex in {male,female}, Embarked in {C,Q,S} | Every batch |
| Missing rate bounds | Age missing < 30% (train baseline: 20%), Cabin missing < 90% (baseline: 77%) | Every batch |

#### Upstream Data Quality

| Source | Freshness SLA | Completeness Check | Quality Check |
|--------|--------------|-------------------|--------------|
| Passenger manifest | N/A (static) | < 25% missing Age, < 85% missing Cabin | No duplicate PassengerIds; all Pclass in {1,2,3} |

## Alerting Strategy

### Applicability

**Not applicable for this project.** There is no running service to alert on. The single Kaggle score is checked manually.

### Educational: Alert Levels for Production

| Level | Definition | Response Time | Escalation |
|-------|-----------|---------------|-----------|
| Info | Feature drift detected (warning threshold) but prediction quality stable | Next business day | None — log and monitor |
| Warning | Prediction accuracy drops below 82% or data drift exceeds warning thresholds | Within 4 hours | Model owner (Thibauld) |
| Critical | Accuracy drops below 80% (BSC2 minimum), pipeline failure, or schema violation | Within 1 hour | Model owner → Team manager (Bart Mollet) |

### Educational: Alert Configuration

| Alert | Metric | Condition | Level | Channel | Recipient |
|-------|--------|-----------|-------|---------|-----------|
| Feature drift | KS/Chi-sq p-value | Warning threshold breached for ≥2 features | Warning | Email | Model owner |
| Prediction shift | Mean P(survived) | Shift >0.05 from baseline | Warning | Email | Model owner |
| Performance degradation | Rolling accuracy | < 82% for 7 consecutive days | Warning | Email + Slack | Model owner |
| Performance critical | Rolling accuracy | < 80% for 3 consecutive days | Critical | Email + Slack + PagerDuty | Model owner + Team manager |
| Pipeline failure | Batch job status | Job fails or does not complete by SLA | Critical | Email + Slack | Infrastructure owner |
| Schema violation | Input validation | Any schema check fails | Critical | Email + Slack | Data pipeline owner |

### Educational: On-call Procedures

| Scenario | Investigation Steps | Resolution Steps | Escalation |
|----------|-------------------|-----------------|-----------|
| Data drift alert | 1. Check which features drifted. 2. Compare current vs reference distributions. 3. Identify root cause (upstream change, seasonal shift, data error). | 1. If data error: fix upstream. 2. If genuine shift: evaluate model on recent data. 3. If performance OK: update reference window. 4. If degraded: trigger retraining. | Team manager if cause is unclear after 4 hours |
| Performance degradation | 1. Confirm with held-out actuals. 2. Check for data drift. 3. Check for pipeline bugs. 4. Analyze errors by subgroup (Sex, Pclass, Age). | 1. If drift-related: retrain. 2. If bug: fix pipeline. 3. If fundamental shift: reassess model family. | Team manager if accuracy < 80% |
| Pipeline failure | 1. Check job logs. 2. Verify input data availability. 3. Check compute resources. 4. Test pipeline manually. | 1. Restart job. 2. Fix root cause. 3. Verify output quality. | Infrastructure team if not resolved in 30 minutes |
| Prediction anomaly | 1. Check prediction distribution. 2. Compare to recent batches. 3. Check input data for anomalies. | 1. If input anomaly: trace to source. 2. If model issue: investigate high-confidence errors. 3. Consider fallback to previous model version. | Team manager |

## Retraining Strategy

### Applicability

**Not applicable for this project.** The model is trained once and submitted once. There is no retraining cycle.

### Educational: Retraining Triggers for Production

| Trigger Type | Condition | Action |
|-------------|-----------|--------|
| Scheduled | First Monday of each quarter | Automatic retraining pipeline with latest data |
| Performance-based | Rolling accuracy < 82% for 7 consecutive days | Manual review → retraining with investigation |
| Drift-based | ≥3 features exceed warning drift thresholds simultaneously | Automatic retraining with expanded feature monitoring |
| Event-based | Major upstream data source change, new feature availability, or business process change | Manual retraining with updated feature engineering |

### Educational: Retraining Pipeline

1. **Collect data** — Pull latest labeled data from the data warehouse (last 24 months)
2. **Run data preparation** — Execute `src/cleaning.py` and `src/features.py` on new data
3. **Split** — Stratified 80/20 train/validation split (or 5-fold CV for small datasets)
4. **Train** — Fit XGBoost with current hyperparameters; log to MLflow
5. **Evaluate** — Compare retrained model to production model on validation set
6. **Validate** — Pass validation gates (see below)
7. **Deploy** — If gates pass, register new model version in MLflow and swap into serving
8. **Monitor** — Watch prediction distribution for 48 hours post-deployment

### Educational: Validation Gates for Retrained Models

| Gate | Criterion | Threshold |
|------|-----------|-----------|
| Absolute performance | Accuracy on holdout set | >= 80% (BSC2) |
| Regression check | Accuracy >= current production model accuracy | No regression (or < 0.5pp drop with justification) |
| Data quality | Training data passes all schema and quality checks | Pass |
| Subgroup stability | No subgroup (Sex x Pclass) drops >5pp from baseline | Pass |
| Prediction distribution | Mean P(survived) within 0.05 of production model | Pass |

### Educational: Data Window

- **Training window:** All available labeled data (expanding window)
- **Rationale:** For this small dataset (891 rows), every data point matters. In a production setting with growing data, a sliding window (e.g., last 24 months) would balance recency with volume.
- **Window type:** Expanding (use all historical data)

## Maintenance Procedures

### Applicability

For this project, maintenance is limited to **preserving reproducibility** — ensuring the model can be retrained and predictions regenerated from the same code and data.

### Actual Maintenance Tasks

| Task | Frequency | Owner | Procedure |
|------|-----------|-------|-----------|
| Verify reproducibility | Once (after submission) | Thibauld | Re-run pipeline from scratch; confirm identical predictions |
| Archive model artifacts | Once (after submission) | Thibauld | Ensure MLflow run `xgboost-tuned-20260331` and all artifacts are preserved |
| Pin dependencies | Once (before submission) | Thibauld | Freeze `requirements.txt` with exact versions |

### Educational: Scheduled Maintenance for Production

| Task | Frequency | Owner | Procedure |
|------|-----------|-------|-----------|
| Dependency updates | Quarterly | MLOps | Review and update Python packages; test pipeline with new versions; update `requirements.txt` |
| Infrastructure patches | Monthly | Infrastructure | Apply OS and platform security patches to serving environment |
| Log rotation | Weekly | Infrastructure | Rotate prediction logs; archive to cold storage after 90 days |
| Dashboard review | Monthly | Model owner | Review monitoring dashboard; adjust thresholds if needed; close resolved alerts |
| Model card update | Per retraining | Model owner | Update metrics, data version, and known limitations in model card |

### Model Versioning

- **Registry:** MLflow Model Registry (local)
- **Naming convention:** `titanic-survival/v{major}.{minor}` (e.g., `titanic-survival/v1.0`)
- **Current version:** v1.0 (XGBoost tuned, run ID `xgboost-tuned-20260331`)
- **Retention:** Keep all versions for this learning project; in production, retain last 3 versions + any version that was ever in production

### Data Retention

| Data Type | Retention Period | Storage | Deletion Policy |
|-----------|-----------------|---------|----------------|
| Raw data (train/test CSV) | Indefinite | `data/raw/titanic/` (git) | Never delete — immutable source |
| Processed data | Indefinite | `data/processed/` (git) | Regenerable from pipeline; safe to delete |
| Predictions (submission CSV) | Indefinite | `submissions/` (git) | Keep all submissions |
| Model artifacts | Indefinite | MLflow (`mlruns/`) | Keep all for reproducibility |
| Monitoring metrics | N/A | N/A | N/A for this project |

**GDPR note:** This dataset contains historical data from 1912. All individuals are deceased. No PII concerns, no GDPR retention limits, no data subject rights applicable (confirmed in 1.2, A1.2-6).

### Decommissioning Criteria

| Criterion | Description |
|-----------|-------------|
| Project completion | Model is decommissioned when CRISP-DM Phase 6 is complete and the final report is written |
| Kaggle competition closure | If the Kaggle Titanic competition is retired, the submission becomes historical |
| Superseded model | If a new model is trained that significantly outperforms this one (>2pp accuracy gain) |

**Decommissioning procedure (for production):**
1. Confirm replacement model is deployed and stable (7+ days in production)
2. Route all traffic to replacement model
3. Archive old model version in MLflow (do not delete)
4. Update model card status to "Retired"
5. Retain monitoring data for 90 days post-retirement
6. Remove old model from serving infrastructure
